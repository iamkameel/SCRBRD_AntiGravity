# SCRBRD 3-Phase Scoring

## Overview

In SCRBRD, **3-phase scoring** is a result-first scoring model designed to keep live cricket scoring fast, accurate and legally reliable while still capturing the richer delivery-level data that powers analytics, coaching, scouting and player development.

The three phases are:

1. **Score** — capture the official result of the delivery.
2. **Enrich** — add cricket context and intelligence.
3. **Verify** — review, complete and amend the data where necessary.

The core principle is:

> **Never sacrifice the score in order to collect analytics.**

Phase 1 is always authoritative. Phases 2 and 3 progressively enrich and validate the event without blocking live scoring.

---

# Phase 1 — SCORE

## Purpose

Phase 1 captures **what officially happened on the delivery**.

It must be fast enough that a scorer can keep pace with live cricket without falling behind.

Typical interaction:

**Bowler → Batter → Delivery → Outcome**

Examples:

- Rabada to Smith → 4 runs
- Rabada to Smith → wicket, caught
- Rabada to Smith → wide
- Rabada to Smith → no-ball + 2 runs
- Rabada to Smith → dot ball

## Core Data

Phase 1 records the authoritative scoring information required to maintain the match state, including:

- Runs off the bat
- Extras
  - Wides
  - No-balls
  - Byes
  - Leg byes
  - Penalty runs where applicable
- Wickets
- Dismissal type
- Batter
- Bowler
- Legal / illegal delivery state
- Over and ball position
- Strike state
- Free-hit state where applicable

## Immediate System Updates

Once Phase 1 is committed, SCRBRD immediately recalculates:

- Team score
- Wickets
- Overs
- Balls
- Striker and non-striker
- Bowler figures
- Batter figures
- Partnership
- Extras
- Fall of wickets
- Required run rate
- Target state
- Innings state
- Scorecard
- Match state

## UX Principle

Common scoring actions should require as few interactions as possible.

For example:

```text
BALL BOWLED
    ↓
[ 0 ] [ 1 ] [ 2 ] [ 3 ] [ 4 ] [ 6 ]
[ W ] [ WD ] [ NB ] [ B ] [ LB ]
    ↓
SCORE COMMITTED
```

A boundary should not require the scorer to enter pitch location, shot type or fielding information before the score is saved.

If the scorer is under pressure, SCRBRD must be capable of operating entirely from Phase 1.

# Phase 2 — ENRICH

## Purpose

Phase 2 captures **how the delivery happened**.

This is where SCRBRD begins turning a traditional scorecard into a delivery-level cricket intelligence dataset.

Phase 2 happens only after the official result has safely been committed.

## Potential Enrichment Data

Depending on the competition, scorer mode and available data, enrichment may include:

### Delivery Data

- Line
- Length
- Pitch location
- Delivery type
- Bowling approach
- Pace / spin classification
- Variation
- Over / around the wicket

### Batting Data

- Shot type
- Shot intent
- Contact quality
- Batting zone
- Front-foot / back-foot
- Attacking / defensive intent

### Wagon-Wheel Data

- Shot direction
- Field segment
- Distance / depth
- Grounded or aerial
- Boundary location

### Fielding Data

- Fielder involved
- Catch location
- Run-out involvement
- Misfield
- Save
- Throw
- Fielding position

### Dismissal Context

- Catcher
- Run-out participants
- Stumping
- Bowled location
- LBW context
- Shot associated with dismissal

## Example

Phase 1:

> FOUR

Phase 2 enrichment:

```text
Bowler: Rabada
Batter: Smith

Result: 4 runs
Length: Good length
Line: Outside off
Shot: Cover drive
Direction: Deep cover
Contact: Grounded
Intent: Attacking
```

The event can now be represented as:

> Rabada to Smith — good length outside off, driven through deep cover for four.

# Phase 3 — VERIFY

## Purpose

Phase 3 protects **data quality, auditability and completeness**.

It allows the scorer or authorised match official to:

- Review incomplete deliveries
- Complete missing enrichment
- Correct scoring mistakes
- Amend dismissal details
- Resolve ambiguous events
- Confirm innings records
- Validate scorecard totals

Verification can happen during natural breaks in play rather than interrupting live scoring.

Suitable moments include:

- End of an over
- Drinks break
- Rain delay
- Innings break
- End of match
- Post-match review

---

# Incomplete Delivery Handling

A delivery can remain legally complete even if analytics are incomplete.

Example:

```text
12.4 — FOUR
Score: Complete
Analytics: Incomplete
⚠ Shot data missing
```

The scorer can later add:

```text
Pitch: Full outside off
Shot: Drive
Direction: Extra cover
Contact: Grounded
```

The official score never needs to wait for this information.

---

# Corrections and Amendments

SCRBRD should never silently overwrite a committed scoring event.

Instead, changes should be recorded through an auditable amendment process.

Example:

```text
Original event
12.4 — FOUR

Amendment
12.4 — THREE

Reason
Boundary signal corrected by umpire
```

The system records:

- Original value
- New value
- Person making the amendment
- Timestamp
- Reason, where required
- Related scoring event
- Updated calculated match state

Conceptually:

```text
ORIGINAL EVENT
      ↓
AMENDMENT EVENT
      ↓
DETERMINISTIC RECALCULATION
      ↓
UPDATED MATCH STATE
```

This fits SCRBRD's event-sourced scoring architecture.

# Operating Modes

The 3-phase model allows SCRBRD to support different levels of scoring sophistication without maintaining separate scoring engines.

| Mode | Phase 1 | Phase 2 | Phase 3 | Typical Use |
|---|---|---|---|---|
| **Quick** | Full | Minimal / optional | Later | Parent, volunteer or fast scoring |
| **Standard** | Full | Selected enrichment | Yes | Normal school cricket |
| **Full** | Full | Complete | Yes | Elite scoring, scouting and performance analysis |

All modes produce the same authoritative cricket score.

The difference is the richness of the surrounding delivery-level dataset.

---

# Quick Mode

Designed for:

- Parent scorers
- Volunteer scorers
- Lower-level fixtures
- Mobile-only scoring
- Situations with limited scorer experience

Priority:

> Keep the scoreboard accurate and keep up with play.

The scorer can primarily use Phase 1 and add limited enrichment when convenient.

---

# Standard Mode

Designed for:

- Regular school fixtures
- Trained school scorers
- Coaches
- Team managers

Captures:

- Complete scoring data
- Shot direction
- Basic pitch data
- Shot type
- Relevant fielding events
- Basic dismissal context

This should be the default SCRBRD experience for most school cricket.

---

# Full Mode

Designed for:

- High-performance cricket
- Professional or dedicated scorers
- Scouts
- Analysts
- Representative tournaments
- Talent identification programmes

Captures the richest available delivery dataset, including:

- Detailed line and length
- Delivery classification
- Shot classification
- Wagon-wheel position
- Intent
- Contact quality
- Field positioning
- Dismissal context
- Batter-v-bowler intelligence
- Performance metadata

# Why Result-First Scoring Matters

A rigid scoring workflow might require:

```text
Pitch → Direction → Outcome → Shot → Commit
```

This creates a serious operational risk.

If several interactions are required before SCRBRD even knows that a batter scored four runs, the scorer can fall behind the live match.

The 3-phase model changes this to:

```text
FOUR → COMMIT
```

followed by optional enrichment:

```text
Pitch → Direction → Shot
```

The scoreboard is therefore correct almost immediately.

Rich analytics can be added seconds later or during a natural pause.

---

# Design Principles

The 3-phase scoring system should follow these rules.

## 1. Score First

The authoritative scoring result always has priority.

## 2. Progressive Enrichment

Analytics are added progressively rather than being mandatory before a delivery can be committed.

## 3. Never Block the Next Ball

The scorer must always be able to abandon enrichment and immediately score the next delivery.

## 4. Legal Cricket State Is Deterministic

Match state must be calculated from the scoring event stream rather than manually edited totals.

## 5. Corrections Are Auditable

Committed events are amended rather than silently overwritten.

## 6. Analytics Are Optional, Score Integrity Is Not

Missing wagon-wheel or shot information must never invalidate a legally correct scoring event.

## 7. One Scoring Engine

Quick, Standard and Full modes should use the same underlying scoring engine and event schema.

## 8. Offline-First

All three phases must continue functioning when connectivity is unavailable, with events synchronised once connectivity returns.

# Relationship to SCRBRD's Event-Sourced Architecture

The 3-phase model fits naturally into SCRBRD's proposed append-only scoring system.

Phase 1 creates the authoritative delivery event.

Phase 2 can either enrich that event through an associated enrichment record or append enrichment data using an auditable update mechanism.

Phase 3 records corrections and verification.

The match state is then rebuilt through a deterministic reducer.

```text
Delivery Events
      +
Enrichment Events
      +
Amendment Events
      ↓
Deterministic Reducer
      ↓
Current Match State
      ↓
Scorecards + Analytics + Dashboards
```

This provides:

- Reliable replay
- Offline synchronisation
- Audit history
- Conflict handling
- Scorecard reconstruction
- Analytics reconstruction
- Historical backfill compatibility

# Strategic Value for SCRBRD

Traditional cricket scoring primarily answers:

> What was the score?

SCRBRD should also be capable of answering:

> How was the score produced?

and eventually:

> Why did it happen, what patterns are emerging, and what should the player or team do next?

The three phases therefore correspond to three layers of product value:

```text
PHASE 1
SCORE
"What happened?"
        ↓
PHASE 2
INTELLIGENCE
"How did it happen?"
        ↓
PHASE 3
TRUST
"Is the data complete and correct?"
```

Together, they allow SCRBRD to remain fast enough for grassroots school cricket while building the high-resolution cricket dataset required for advanced coaching, scouting and match intelligence.

---

# Definition

**SCRBRD 3-Phase Scoring** is a progressive cricket scoring architecture where the official delivery result is captured first, contextual performance data is added second, and the complete event is reviewed and verified third.

Its purpose is to ensure that:

> **Live scoring remains fast, cricket remains accurate, and analytics become richer without one compromising the other.**
